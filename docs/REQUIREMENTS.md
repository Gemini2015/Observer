## 1. 项目定位

Observer（观测者）是一个**多机文件完整性巡检与修复系统**：

- 一个中心服（Hub）统一管理多台机器上的挂载点（mount）；
- 每台机器部署一个 agent（哨兵），按中心服下发的任务定期计算文件哈希；
- 哈希与基线一起入库，与基线不一致即视为「疑似损坏」，发出提醒；
- 同一个文件如果在你多台机器上都有副本，可以从健康副本恢复到损坏的机器。

一句话：**定期验一遍文件还是不是原来那份，坏了立刻知道，并能从别的机器补回来。**

### 1.1 命名

- 项目名：Observer（观测者）；仓库 `observer`。
- 隐喻：一次哈希 = 对文件的一次「观测」；入库的哈希 = 「观测记录」；不一致 = 「偏离」（divergence，暂定术语）。
- 派生标识符（`observer` / `observer-agent` / `OBSERVER_*`）均为暂定，见 [README](../README.md)。

## 2. 背景与问题

✅ 已确认的问题：

1. 长期存放的文件可能发生**静默损坏**（bit rot、磁盘坏道、控制器/内存/文件系统/传输错误等），表现为内容变了，但文件大小、修改时间可能都不变；
2. 用户不会主动发现，往往要等某天打开照片/视频才发现已经损坏，那时可能已经没有好副本；
3. 多机冗余（NAS + 台式机 + 笔记本 + 移动硬盘）天然构成多副本，但**缺少统一的「哪份是好的」的记录**；
4. 即使发现某台机器上的副本坏了，也需要**方便地把另一台机器上的好副本复制过来**。

> 补充：只比较文件大小/修改时间不足以发现静默损坏——损坏可以发生在内容层面而元数据不变，所以必须比对内容哈希。

## 3. 目标与非目标

### 3.1 目标（✅ 已确认）

- **G1** 对指定目录/文件做定期哈希巡检；
- **G2** 哈希基线入库，可追溯（何时、哪台机器、哪个路径、什么算法）；
- **G3** 发现哈希与基线不一致时提醒用户；
- **G4** 多机副本可互相对照，支持从健康副本修复损坏副本；
- **G5** 覆盖 Windows / macOS / Linux（NAS 容器）三类运行环境；
- **G6** 中心服负责全局视图、任务派发与执行记录。

### 3.2 非目标（✅ 已确认 / 🟡 初稿）

- ✅ 不是备份、同步、去重工具，不负责把文件变多或变一致；
- ✅ 不承诺「防止」比特腐烂——物理层面做不到，Observer 只负责**发现**；
- ✅ 不自动修改文件：告警只是告警，是否修复由人工确认；
- 🟡 不做文件内容加密 / 端到端加密；
- 🟡 暂不处理云盘 API（网盘挂载成本地盘的情况另议）；
- 🟡 暂不做块级校验或纠删码（par2 式），先跑通文件级哈希（见 §10-I）。

## 4. 角色与典型场景

### 4.1 角色

- ✅ 单一用户（个人/家庭），多台机器，一个中心服；
- 🟡 暂不做多租户/团队协作（见 §10-F）。

### 4.2 场景

**S1 建基线**：新机器接入 → 注册 agent → 选择挂载点与排除规则 → 首次全量计算哈希 → 入库作为基线。

**S2 定期巡检**：中心服按计划给各 agent 下发巡检任务 → agent 本地计算/比对 → 上报结果 → 中心服更新记录与状态。

**S3 发现异常**：某文件哈希与基线不一致（或文件丢失/不可读）→ 生成异常 → Web 提醒 + 可选通知渠道 → 用户人工确认。

**S4 跨机修复**：确认机器 A 的 `/photos/x.jpg` 损坏、机器 B 上有健康副本 → 在 Web 上选择「从 B 恢复到 A」→ 传输并校验 → 重新哈希确认 → 关闭异常。

**S5 日常查看**：Web 总览看到各机器在线状态、最近巡检时间、异常列表、目录概况。

## 5. 已确认需求（功能）

> 编号用于后续讨论引用；验收要点只写方向，细节随讨论补充。

| 编号 | 需求 | 验收要点（方向） |
| --- | --- | --- |
| FR-1 | **挂载点登记**：在中心服为某台机器添加/移除挂载点（mount），支持 include / exclude 规则 | 可增删改；`mount_id` 稳定不可变；include 白名单与 exclude 黑名单生效（exclude 优先）；规则带版本号；规则收紧后旧文件转 `out_of_scope` 而非「丢失」；同机挂载路径不得重叠/嵌套；挂载缺失时熔断，不得报「全盘丢失」 |
| FR-2 | **基线**：首次对 mount 做全量哈希并入库 | 可见进度；无权限/失败文件有记录；基线可重建 |
| FR-3 | **周期巡检**：按计划（全局默认 + 每 mount 覆盖）执行，支持手动触发 | 计划可配；可错峰；可中断/续跑 |
| FR-4 | **增量策略**：不要求每次都全量重算 | 大小/修改时间未变的文件可跳过，并标明「本轮跳过」（已定：size + mtime_ns + 90 天全量兜底，见技术方案 A2） |
| FR-5 | **哈希入库**：文件身份 + 哈希 + 时间 + 机器/路径 | 可查询单文件历史；可导出 |
| FR-6 | **异常检测与告警** | 不一致/丢失/不可读分别成异常；Web 可见；可确认/忽略 |
| FR-7 | **多机管理** | agent 注册（一次性 token）、在线状态、心跳、离线标记 |
| FR-8 | **任务派发与执行记录** | 中心服下发任务、agent 执行并回报；失败可重试；有执行日志 |
| FR-9 | **副本关联** | 同一文件在多机上的记录可被关联/建议关联（已定：内容哈希全等） |
| FR-10 | **人工确认后修复** | 指定源/目标；默认不自动执行；可先隔离坏文件；传输后校验 |
| FR-11 | **Web 界面** | 总览、机器、目录、文件详情、异常、任务、设置 |
| FR-12 | **审计日志** | 谁在何时触发了什么、结果如何 |

## 6. 已知平台与部署约束

| 项 | 已确认 | 备注 |
| --- | --- | --- |
| 中心服 | Node.js 实现的 Web Server，负责全局管理与任务派发 | 运行在一台常开机器（如 NAS 或小主机） |
| Agent · Windows | Go + Wails GUI 客户端（普通程序，非系统服务） | 托盘/后台/开机启动；连接状态、巡检进度、异常 |
| Agent · macOS | Go + Wails GUI 客户端（普通程序，非系统服务） | 同上；签名与公证待定 |
| Agent · Linux | 无 GUI 的 Go 单二进制，systemd 或 Docker 运行（NAS） | 只读挂载；UID/GID 可配 |
| Agent 技术栈 | Go（≥1.24），核心零 CGO；桌面壳用 Wails v3 + 系统 WebView | 一套核心两种形态，详见技术方案 |
| 通信协议 | HTTPS + REST + 轮询（心跳 15s，可长轮询 25s） | agent 主动连中心服；不用 WebSocket/gRPC |
| 存储 | SQLite（WAL），单文件 | 百万级文件规模；每日快照 |
| 前端 | React + Vite（中心服 Web 与桌面 GUI 同栈） | |
| 哈希 | SHA-256 流式，记录算法字段 | 未来可切 BLAKE3 等 |
| 网络 | 以局域网为主；agent 主动连接中心服 | 默认仅局域网；公网访问需反代 + TLS（E4 已定） |
| 数据规模 | 照片/视频为主，单文件可达 GB 级，总量 TB 级 | 设计目标：百万文件、TB 级；单文件无硬上限（流式读取） |
| 运行形态 | 中心服常开；agent 常驻/定时 | 桌面为普通程序（托盘 + 开机启动），不做系统服务；NAS 用 systemd 或容器 |

## 7. 非功能需求（初稿）

- 🟡 **性能**：大文件流式读取（1MiB 缓冲，不做文件内断点）；双闸限速（`bytes_per_sec` + `files_per_sec`，文件为原子单位、长期平均）；夜间窗口 + 每日时间预算；并发默认按磁盘类型。
- 🟡 **可靠性**：断点粒度为单个文件、批次幂等可重试；中心服重启不丢任务；agent 离线时结果进本地 spool，恢复后补发。
- 🟡 **可观测**：结构化日志、健康检查、任务耗时/吞吐统计。
- 🟡 **安全**：agent 用 token 鉴权；传输 TLS（可自签）；agent 最小权限；防路径穿越；Web 登录（已定：单用户密码会话）。
- 🟡 **可部署**：中心服 docker compose 一键起；agent 单文件/单镜像，配置从文件或环境变量读。
- 🟡 **兼容**：Windows 10+、macOS（❓版本）、Linux x86_64/arm64（NAS）。
- 🟡 **资源占用**：桌面闲置 ≤120MB / 扫描 ≤200MB（含 WebView）；NAS 闲置 ≤30MB / 扫描 ≤80MB；IO 与 CPU 由限速器约束。

## 8. 概念模型（草案，不落 schema）

```
machine ──< mount ──< file ──< hash_record
                        │
                        └──< issue（异常）
replica_group >── file（跨机器关联同一份内容）
repair_job >── issue / replica_group
scan_job >── mount
```

| 实体 | 说明 |
| --- | --- |
| machine | 一台机器：agent 信息、在线状态、平台 |
| mount | 机器上的挂载点（受管目录）：稳定 `mount_id`、可变 `label`、物理路径、`sentinel`、`fs_kind`、排除规则、巡检计划 |
| file | mount 下的一个文件：相对路径、大小、mtime 等 |
| hash_record | 一次观测：算法、哈希值、时间、来源（基线/巡检/修复后） |
| scan_job | 一次巡检任务：mount、范围、状态、统计 |
| issue | 异常：类型（mismatch / missing / unreadable）、级别、状态（待确认/已确认/已忽略/已修复） |
| replica_group | 同一内容在多机上的关联（已定：内容哈希全等） |
| repair_job | 一次修复：源/目标、进度、校验结果 |

路径身份：逻辑路径 = `mount_id` + 相对路径，物理路径只作 mount 元数据、不进入身份。
详见 [路径与身份模型](DESIGN-PATH-MODEL.md)。

## 9. 典型流程

### 9.1 建基线

1. 中心服创建 agent 注册 token；
2. 机器上安装 agent，用 token 注册并上报机器信息；
3. Web 上选择目录、配置排除规则；
4. 下发基线任务 → agent 全量哈希 → 上报 → 入库。

### 9.2 定期巡检

1. 调度器按计划生成 scan_job；
2. 中心服把任务下发给对应 agent（支持队列、并发与超时）；
3. agent 遍历 mount，按增量策略计算哈希；
4. 上报结果：一致 / 不一致 / 丢失 / 不可读 / 跳过；
5. 中心服更新 hash_record 与状态，生成或关闭 issue。

### 9.3 异常与修复

1. 出现 issue → Web 提醒（可选通知渠道）；
2. 用户查看：同文件在各机器上的记录、哈希、时间；
3. 人工确认损坏 → 选择健康副本 → 下发 repair_job；
4. 先把坏文件移到隔离目录（默认开启，保留期与容量可配）；
5. 经中心服中转传输（分块续传）→ 校验哈希 → 原子替换；
6. 复核通过 → issue 关闭，记录修复历史。

## 10. 待讨论问题（下次讨论议程）

> 每条都可以直接回答「要/不要、选哪个」，回答后回填到上文对应章节。
>
> **v0.4 状态**：A–I 与 J 两组均已全部定稿，结论见 [技术方案](DESIGN-TECH.md) §3.2 的逐条对照与 [路径与身份模型](DESIGN-PATH-MODEL.md) §8；本节保留原始问题便于追溯。

### A. 校验策略

- **A1** 哈希算法：BLAKE3 / SHA-256 / 其它？是否需要保留算法字段以便未来切换？
- **A2** 大小 + 修改时间未变就跳过，是否可接受？需要多长周期做一次「全量兜底」？
- **A3** 文件移动/重命名如何识别（避免重新建基线）？
- **A4** 排除规则：系统目录、回收站、缩略图缓存、临时文件？
- **A5** 硬链接、符号链接、稀疏文件、网络盘（SMB/NFS）怎么处理？
- **A6** 是否需要校验元数据（权限/属主/时间戳/xattr），还是只校验内容？

### B. 性能与资源

- **B1** 单文件最大值、文件总量级（决定分块与并发策略）；
- **B2** IO 限速、CPU 占用的默认值；
- **B3** 巡检时间窗（夜间/空闲时）、错峰策略。

### C. 数据与历史

- **C1** 哈希历史保留多久/多少条？只保留当前 + 变更历史？
- **C2** 数据库选型：SQLite 起步还是直接 Postgres？
- **C3** 中心服自身数据（配置、哈希库）怎么备份？

### D. 副本与修复

- **D1** 「同一份文件」如何判定：大小 + 路径后缀 + 哈希？还是全靠人工确认？
- **D2** 修复传输走 agent↔agent 直连，还是经中心服中转？是否需要断点续传/加密？
- **D3** 覆盖前是否先隔离坏文件（保留证据）？
- **D4** 源只读、目标只写的最小权限怎么设计？

### E. 多机与网络

- **E1** agent 与中心服的通道：HTTP 轮询 / WebSocket / gRPC？
- **E2** 离线期间的任务如何补跑？重试策略？
- **E3** 时钟不一致如何处理（以中心服时间为准）？
- **E4** 是否需要跨网段/公网访问？如何认证？

### F. 安全与用户

- **F1** 单用户还是多用户/多租户？Web 是否需要登录？
- **F2** token 模型：注册 token、长期 token、轮换？
- **F3** TLS：自签 / 反向代理 / 内网明文？
- **F4** agent 权限：只读挂载？以什么用户运行？

### G. Agent 技术栈

- **G1** 语言：Go 还是 Rust（单文件、跨平台、静态链接）？
- **G2** GUI：托盘 + 原生窗口 / WebView / 本地 Web UI？
- **G3** Windows 服务化、macOS 签名与公证、Linux 容器挂载与 UID/GID？

### H. 告警

- **H1** 渠道：Web 内 + 邮件 / webhook / IM？
- **H2** 聚合与静默：批量异常如何合并？如何避免重复提醒？

### I. 范围边界

- **I1** 是否需要块级校验/纠删码（par2 式）？
- **I2** 是否支持云盘、对象存储？
- **I3** 是否需要「文件版本」概念，还是只关心「当前是否与基线一致」？
- **I4** 是否需要 CLI？

### J. 路径与身份（v0.2 新增，详见 [路径与身份模型](DESIGN-PATH-MODEL.md)）

- **J1** 全局引用串用 `observer://<machine>/<mount>/<relpath>`。（✅ 已采纳；`machine:mount:/relpath` 备选不再使用）
- **J2** 保留 `mount:/relpath` 短形式，仅限机器已知上下文。（✅ 已采纳）
- **J3** `root` 全文更名 `mount`。（✅ 已于 v0.2 采纳）
- **J4** 中文术语用「挂载点」，首次出现注明「受管目录」。（✅ 已采纳）
- **J5** 相对路径折叠 `//` 与 `.` 段。（✅ 已采纳）
- **J6** `machine_id` 由 **agent 配置声明**，hub 校验格式并按它归并机器；同机多 agent 共享同一 `machine_id`（`mount_id` 冲突拒绝）；改名走迁移操作。（✅ 已采纳，替换「由 hub 注册时分配」的旧建议）

## 12. 术语表

| 中文 | 英文 | 说明 |
| --- | --- | --- |
| 中心服 | hub / server | 全局管理、哈希库、任务派发 |
